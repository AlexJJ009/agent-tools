## 1. 要解决的问题

Agent Tools 在开发过程中同时生成结构化任务记录、Markdown 状态视图、检查证据、报告和事件副本。Agent 还需手工维护其中部分内容，容易造成重复、过时、遗漏更新和恢复困难。简单把这些文件移到另一个目录，不能解决生命周期和上下文污染。

当前代码中，`agent_workflow/runtime.py` 创建 `request.txt`、`checklist.yaml` 和 `task.md`，检查产生 evidence 文件，schema 2 还导出 `events.json`；`learning_workflow/runtime.py` 维护另一组路由数据。现有实现已经包含原子文件写入、revision 冲突检查、证据关联和作用域受限的 Hook，不应因改造而丢失这些能力。这里是代码观察，不是对全部部署现场的结论。

本 MVP 的结果是：一个任务可以在同一机器的多个对话里协商、开发、验证和验收；runtime 维护一份当前状态；用户接受后，Cleaner 把有长期价值的信息维护到项目已有载体，清理失效过程材料；其他项目、worktree 和任务不受影响。

### 1.1 用户已确认的约束

以下是对话原文及其含义，原文不作为关键词触发规则：

- “是的，继续用python。”——继续 Python，不进行语言重写。
- “一个task可以在不同的codex对话里去实现和协商确定需求；worktree只是工作现场而已。”——task 不归某个 session 所有。
- “会在不同的机器上去使用，但这些东西不会跨机器保存。”——软件多机部署，各机独立数据，无跨机器同步。
- “agent需要输出的是需要check的点，而checklist的生成维护应该是软件来完成的。”——语义条件由 Agent 提出，列表与状态由 runtime 维护。
- “自动清理的职责可以落实到 clearner 去完成执行。”——Cleaner 负责收尾整理的语义判断和调用。
- “项目的文档我们肯定不清理”——项目交付文档不进入自动删除范围。
- “包括 work-report 都是我们要清理的”——报告不因文件类型而永久保留。
- “是否遗漏用户要求，这个应该是用户和Agent一起校对，例如PRD。”——程序不声称自动证明需求完整。
- “例如，写 work-report 需要遵循写作原则，如果没遵循，说明失败。”——文件存在和格式通过不等于质量通过。

### 1.2 需要纠正的行为

1. 修改需求后另开一份 PRD/checklist，留下多个竞争的当前版本。
2. 读取状态也产生新文件，或反复运行检查无限积累相同用途的材料。
3. 新对话默认读取全部历史，把旧结论当成当前事实。
4. 把测试通过等同于用户验收通过。
5. 为了文件登记，阻止普通代码和项目文档编辑。
6. 清理过程文件时破坏测试引用，或误删项目文档、其他任务材料。
7. 只凭合成案例通过或主观感觉，宣称新组件提升模型表现。

## 2. MVP 范围与非目标

### 2.1 必须交付

- 按需创建、查询和原位修订 task；同机跨对话接续。
- 原子状态更新、原子文件发布、写入失败恢复及幂等请求，在 MVP 实现并验证，不推迟到后续版本。
- 四类 checklist 查询：整体、单项状态、单项详情、名称/内容搜索。
- 需求、验证结果、用户验收相互区分，关联版本并识别失效。
- 每机每用户的外置存储，明确 task、workspace、session 和产物归属。
- Cleaner 的 task closeout 场景，以及可恢复、可重试的范围内清理。
- 选定旧任务的显式导入路径；安装升级不破坏旧数据。
- 确定性回归测试、CPU 可运行的简化历史数据集和针对具体机制的验证；模型对照实验按明确假设选做。
- 更新必要接口/安装文档，保留写作规范及独立 review。

### 2.2 不在 MVP 内

跨机器同步、云服务、多人权限系统、Web UI、向量检索、全仓库扫描注册、持续后台守护、完整聊天归档、通用工作流引擎、替换 Harness、强制所有文件走登记门禁。原生 Hook 自动触发不是 MVP 正确性的必要条件。普通短任务无需创建持久 task。

MVP 不要求统一各项目的文档目录，不要求每任务创建 PRD 文件、ADR、报告或新的文档体系。现有正式运行/授权边界不因本改造放宽。

### 2.3 实现建议与已确认需求的区别

SQLite、platformdirs、下文接口名称、状态枚举和表组织是本 PRD 提出的实现方案，供用户校对；它们不是用户此前指定的细节。实现可以沿用现有兼容命令，但不能降低本 PRD 的行为标准。性能数值、日志保留时长和模型实验次数不在没有依据时伪造为硬指标。

## 3. 角色、所有权与工作循环

| 角色 | 责任 | 不负责 |
|---|---|---|
| 用户与 Main Agent | 校对要求、解释反馈、确定接受范围 | 以自动生成状态代替真实反馈 |
| Agent / Skill | 提出检查条件、选择验证、维护必要项目文档、写报告 | 手工同步多份状态副本 |
| Runtime | 保存与查询状态、版本控制、产物归属、范围核验和清理执行 | 自动判断需求完整、文字长期价值或测试语义质量 |
| 独立 Subagent reviewer | 按测试/代码/写作规范检查质量 | 用自身认可替代用户验收 |
| Cleaner | 在明确收尾场景中整理任务过程文档、产物与工作现场，判断材料处置并调用 runtime | 以本 MVP 承担代码质量治理，或接管其他任务/项目文件 |
| 项目自身 | 代码、测试、API/使用文档和必要 ADR | 存放工具内部全部历史 |

建议的任务状态：`draft → active → awaiting_acceptance → closing → closed`。用户未接受时从 `awaiting_acceptance` 回到同一 task 的 `active`；恢复协商可修订当前要求。用户明确接受相关结果才进入 `closing`。清理失败或中断停留在 `closing`，不能标为 closed。

用户反馈由 Agent 理解后连同必要原文和范围写入，不用“完成了”等单词匹配直接触发清理。仅讨论结束机制不是结束授权。部分接受只更新对应验收项，不关闭整个任务。测试通过和 Agent 自称完成都不是用户接受。

任务关闭后再来新要求，若完整任务仍保留可显式重开；已经按策略清除内容则不能宣称可恢复原 PRD，须基于项目现状建立新的任务。关闭与销毁存储是不同动作。

## 4. 身份、范围与接续

- `task_id` 是独立稳定标识，不取 session ID、分支名或目录名充当。
- `workspace_id` 标识本机工作现场，关联仓库 common directory、worktree Git directory 和规范化路径；Git 标识用于定位，不声称路径在移动后不变。
- `session_id → task_id + workspace_id` 是可变绑定。一个 task 可被多个对话先后或同时访问。
- 一个 worktree 可存在多个任务。仅有一个明确活动绑定时可自动恢复；有歧义则返回候选摘要，不猜测，不为查询新建任务。
- 分支、HEAD 和工作区相关内容摘要属于观察与证据版本。切分支不自动转移任务或沿用检查通过状态。
- 本 MVP 的单次操作明确指向一个工作现场。跨 worktree 接续须显式重新关联；不按 remote URL 自动合并，不要求实现多仓库原子任务。
- workspace 移动/删除时返回位置失效，提供重新关联；不能因目录消失就自动删除 task。其他 workspace 的读取、执行和清理保持可用。
- 全局查询只列必要元数据；读取正文必须指定 task。此为软件作用域隔离，不是针对同一 OS 用户的安全沙箱。

## 5. 数据存储与读取

### 5.1 物理存储

数据由 Agent Tools 自己维护。建议在 Linux/WSL 使用 `${XDG_DATA_HOME:-$HOME/.local/share}/agent-tools/`，例如本机 `/home/alex_mercer/.local/share/agent-tools/`；通过 platformdirs 获取平台路径，所有 task 子命令使用同一解析入口。显式 `--data-root` 优先于应用配置，应用配置优先于平台默认值；查询可显示实际绝对路径，不另创建索引文件。

这里的“Agent Tools 的位置”指其应用数据目录，不自动解释为 Git 源码 checkout 或可被升级替换的安装目录。该具体位置仍为待用户校对的建议；如果用户确实指定源码目录内存储，需显式配置并验证 Git 排除、升级及删除 checkout 的后果，不能悄悄采用。本轮 PRD 工作不迁移真实数据；MVP 实现并以隔离样本验证显式导入能力，实际迁移另按选定范围执行。

```text
<data-root>/
  tasks.sqlite3
  artifacts/<task-id>/...
```

SQLite 保存小型结构化数据及当前 PRD 正文；必要的大输出/报告以文件保存。数据库使用本机文件系统，不依赖项目共享挂载。无 HTTP 服务、无同步协议；CLI 进程按需打开数据库。跨机器只部署软件与配置，不复制任务状态。路径名称不是正确性证据：须实测默认目录、显式覆盖、不同 cwd、跨进程恢复、权限失败、两个隔离 data-root，以及安装/升级后的路径一致性；测试只使用隔离用户目录和临时 data-root。

建议逻辑对象：Task、Criterion、CheckResult、UserFeedback、WorkspaceBinding、Artifact、CloseoutOperation。允许用少量表及 JSON 字段表达，不要求引入 ORM 或事件溯源系统。

### 5.2 当前数据与历史

- Task：当前需求正文、范围/排除项、revision、状态及必要恢复说明。
- Criterion：稳定 ID、可变显示顺序、名称、具体要求、预期结果、验证方式、来源引用。
- CheckResult：来源类型（runtime 执行/外部导入）、退出码或观察、检查时间、需求版本、代码及相关输入标识、证据引用。
- UserFeedback：必要原文、来源定位、接受/拒绝的范围及其对应版本。runtime 不认证提交者确实代表用户，不伪称外部身份验证。
- Artifact：task 所有者、用途、位置、内容摘要、引用和处置状态。项目交付文件默认不归清理器所有。
- CloseoutOperation：最小可恢复操作状态，完成后按生命周期回收，不额外渲染清理报告。

不保存每次查询的事件，不复制完整对话，不无界追加整份任务快照。调试日志使用有界保留。当前仍被引用的证据不按单纯时间到期删除；已替代且不再引用的过程材料在修订/收尾维护中回收，活跃引用与用户指定保留优先。

默认关闭且清理后，仅保留用于任务列表和重复操作识别的最小关闭元数据，不含已删除 PRD/报告正文；用户显式保留完整任务或部分材料时，保留对应内容及其必要引用，不受“仅保留元数据”限制。完整要求和状态仍在时允许重开；仅保留一份报告不意味着可恢复完整任务。支持显式彻底忘记已关闭任务。不能以数据库隐藏历史代替文件无限增长。

### 5.3 读取原则

查询默认为当前摘要，详情/证据按需取；不把所有数据当作模型上下文。历史结果明确标注历史和失效，不作为当前依据。代码实现、Git 变更、外部作业运行状态仍从现场读取。

PRD/checklist 是数据的视图。需要给人看时输出 Markdown；默认 stdout 展示不创建文件。用户明确导出时创建一个受管材料或指定项目交付物，并区分所有权。同一导出目标更新原文件，不按阶段复制。外部编辑的 PRD 通过带 revision 的显式导入更新，不能暗中保持两个权威来源。

## 6. Python 操作接口

先复用现有 CLI；内部 Python service 函数与 CLI 共享业务逻辑。Agent 使用稳定 JSON，人可选文本/Markdown。以下是能力契约，不强制具体命令拼写。

| 能力 | 输入重点 | 输出/副作用 |
|---|---|---|
| 创建 task | 工作现场、当前要求、可选调用幂等键 | task ID、revision；仅此时按需建记录 |
| 列表/读取 | task/workspace、摘要/详情选择 | 当前信息；不写文件、不改变 revision |
| 修订 | task、base_revision、目标 ID、变更、必要来源 | 同一 task 新 revision；受影响结果失效 |
| 记录检查 | criterion ID、版本、方法、结果与来源 | 结果及有效性；外部导入不得称 runtime 亲自执行 |
| 记录反馈 | 当前版本、原文/来源、对应范围、Agent 解释 | 用户验收状态；不能隐式扩大接受范围 |
| 收尾/清理 | task、base_revision、语义处置与精确目标 | 计划摘要/执行结果/恢复状态；不默认创建报告 |

检查可继续使用 Harness 原生 Shell 和项目测试命令。MVP 不要求所有命令由 runtime 启动，也不重建作业调度器。

### 6.1 Checklist 四类查询

| 查询 | 必需行为 |
|---|---|
| 整体列表 | 按当前顺序返回 ID、名称、简短要求、验证与用户验收状态、revision |
| 单项状态 | 分开返回 verification、validity、user_acceptance；不只返回一个 completed 布尔值 |
| 单项详情 | 返回具体内容、预期、验证方式、当前证据引用和失效原因 |
| 名称/正文搜索 | 默认只搜当前 task 的当前项；文本匹配返回命中字段与候选 ID；无匹配正常返回空集 |

稳定 ID 如 `AC-005` 不等于第五项。按 ordinal=5 查询返回当前第五项的稳定 ID 和 revision；后续更新使用稳定 ID。不存在/越界明确报错；多匹配不自动挑一个。删除或撤回验收项不复用其 ID，不伪装通过；相关证据按引用处理。无需语义检索或向量库。

建议状态：verification=`not_run/passed/failed/error`；validity=`current/stale/unknown`；user_acceptance=`pending/accepted/rejected/invalidated`。通过测试、技术错误、结果过期和用户拒绝是不同事实。全部“有效通过”也不自动转为用户接受。

### 6.2 一致性与失败

写入检查 base_revision，以短事务更新相关对象；运行测试和模型判断期间不持有写事务。重复调用以操作标识幂等，重放不能重复创建结果/文件。旧 revision 更新必须拒绝且保留当前数据。

相关输入变化后使旧结果失效；若未声明可靠依赖范围，保守标记需要重查，不能只凭同一个 HEAD 判断脏工作区结果有效。保留源码相关内容摘要/配置摘要或等价证据。

原子性、写入和幂等是 MVP 的硬要求，具体契约如下：

1. **数据库原子更新**：一次需求修订及其结果失效、一次反馈及其状态变化必须在同一 SQLite 事务中提交；任何一步失败全部回滚，不暴露部分新状态。schema 迁移同样需要明确失败恢复。不得用“单文件数据库”代替事务设计。
2. **文件原子发布**：受管文件先写入同一文件系统的临时文件，检查完整性并 flush/fsync，再通过原子替换发布；按平台能力同步目录元数据。读者只能看到完整旧版或完整新版；失败不留下被当作完整产物的半写文件。写入协议同时核验所属 task 与目标边界，防止并发覆盖用户已修改的材料。
3. **跨数据库/文件系统恢复**：两者不共享事务。使用短暂准备状态与可恢复操作记录，完整发布后才让产物成为可读的 committed 引用；中断后识别未发布/已发布未提交等阶段，恢复或回收仅由本次操作拥有的残留。不能出现成功结果指向缺失/半写产物，也不能把未知文件当作孤儿自动删除。已有 committed 产物在同一路径被替换时，必须协调读取与发布：数据库旧 revision/摘要不能被作为新版文件的有效描述返回。发布中返回明确的暂不可读/恢复状态，或保证读取取得完整一致版本；崩溃恢复后版本、摘要和内容必须一致，不要求永久保存历史副本。
4. **幂等请求**：创建、修订、记录结果和清理等变更接受稳定 operation_id，按作用域保存请求摘要与结果。同一键同一请求返回原结果，不增加 revision、证据或文件；同一键不同请求返回 idempotency_conflict。同一请求中途崩溃后用原键继续，不能当新操作重复处理。成功请求的重放先验证幂等匹配，不因其原 base_revision 已旧就错误拒绝。
5. **并发与持久化**：版本比较和更新在事务内完成；两个并发相同键只有一次有效提交。数据库 busy/存储满/权限错误不得返回成功，重试有界。正常进程退出及崩溃恢复后核对已提交状态；不宣称超出文件系统保障的绝对断电安全。
6. **清理幂等**：只把此前已确认归属且属于该操作的缺失文件当作已删除；初次就缺失的未知目标不能借幂等规则跳过核验。closeout 未完成前保留恢复信息，恢复后不重复修改其他任务或项目文件。幂等记录保留覆盖活动/收尾/关闭回执周期；显式彻底忘记后不承诺无限期重放仍能找回原结果。

幂等的保证范围是 runtime 的数据/产物操作，不等于对任意外部 Shell、训练或发布命令提供 exactly-once 执行；这些副作用仍须具体适配协议。本 MVP 不为此新增调度系统。

错误区分 not_found、revision_conflict、idempotency_conflict、workspace_mismatch、invalid_input、storage_unavailable 和 cleanup_blocked。存储不可用时不能伪报保存成功，但普通代码/文档编辑不受全局拦截。CLI 错误返回可操作信息与非零退出码。

## 7. Cleaner 收尾和过程材料生命周期

本 MVP 中 Cleaner 的职责是任务过程材料与工作现场整理，不是代码质量治理。此前将其扩展为 formatter/lint、代码风格和通用工程规范执行者属于目标偏移，已撤回。本 PRD 不据此更改现有 Cleaner Skill 的代码整理实现；后续实施需明确本次 task closeout 的触发与组件边界。测试有效性、代码 review 和报告写作质量仍由各自开发/评审能力负责。

用户对任务结果明确接受且完成范围已确定后进入收尾；不以 Stop、会话结束或出现 work-report 字样作为触发。项目已有材料保留、文档位置和 worktree 管理约定优先；没有约定时只按本 PRD 的任务归属、引用、保留要求和恢复规则处理，不自行引入代码质量工具链。

工作现场整理包括查询当前 task 关联的 worktree、原有改动与任务残留，判断是否仍需保留和交接。可使用 Git 状态与 worktree 查询辅助核实，但数量、年龄或未跟踪状态均不能直接决定删除。MVP 默认不自动删除 worktree、分支或其他工作现场；实际移除须有明确范围并遵循已有 worktree 管理能力，不能由过程文件清理顺带执行。其他项目和 worktree 不受影响。

1. 查询当前要求、接受范围、必要证据及本 task 受管材料。
2. 判断哪些信息需要更新到已有代码、测试、使用文档或必要 ADR；优先更新既有载体，无长期价值不创造文档。
3. 检查已知引用和项目实际脚本依赖。需长期保留的测试输入转为项目 fixture，验证迁移后行为；不能让验收依赖可清除 records。
4. 提交精确处置：保留、替代、移交项目维护或删除。移交后该产物退出工具自动删除集合。
5. Runtime 核验所有权、revision、路径和内容未变、当前引用已解除，再执行。
6. 对收尾修改按依赖范围重新验证，再确认无遗留阻塞且处置完成后关闭；否则停留 closing，返回剩余问题。

收尾中的代码、测试或配置变化不能沿用已失效的检查结果。纯文档整理或已证明等价的 fixture 迁移，不机械要求用户重新接受，但仍需核验链接、内容和对应测试；保留原反馈的接受范围，不将其冒充用户对新版本的再次反馈。如果收尾改变了已接受的行为或要求，停止该范围清理，回到同一 task 的 active 状态重新协商和验证，再提交用户验收。

删除只针对登记且经核验的本 task 过程材料，包括 PRD 导出、checklist 导出、work-report、旧证据和 scratch。文件名、扩展名、Git ignored 状态或“由 Agent 写过”均不足以证明所有权。用户标记保留的材料优先；项目文档和其他任务材料禁止删除。

新过程产物默认限制在本 task 的 artifact 根；兼容旧项目内材料须逐项显式接管。拒绝目录逃逸和 symlink 越界；对清理判断后被编辑的文件拒绝删除并返回冲突。未知用途材料保留并提示，不自动收入管理。

文件系统删除与数据库事务不是同一个原子事务。维护有限的 closeout 操作状态，支持逐项确认、中断恢复、幂等重试；不能数据库先标完成而文件仍未处理。完成后的执行记录遵循有界回收，不产生新的清理文档包。恢复机制只保证操作一致性，不保证语义判断永远正确。

报告已生成不等于已读。用户最终接受任务且没有保留要求时，可按约定清理此前已交付过程报告；如果本轮尚有待交付报告，先完成交付，不能删除正在交付的路径。无自动默认“阅读已完成”信号。

## 8. 安装、兼容与组件边界

软件可安装到 WSL 和 Linux 服务器，每个用户拥有独立 data-root；原生 Windows 如声明支持，必须单独验证路径、SQLite 和安装行为。首轮必须验证当前 WSL/Linux 使用面；未经实测的平台不宣称支持。

继续使用现有安装入口及目标配置保护。升级保留数据并检查 schema 版本；迁移前可恢复备份、迁移失败明确停止，旧版本遇到更高 schema 不尝试破坏性写入。备份在验证成功和保留策略满足后回收，不无限积累。卸载默认保留用户数据，彻底清除为显式操作。

旧记录只导入用户/Agent 明确选择的任务。导入保留来源与状态差异，不把旧用户反馈重新解释为新代码已接受；导入核验前不删源数据。不在普通启动时扫描全部仓库，不同时让旧文件与数据库成为可写权威来源。

Skill 保留语义判断和写作规范；plugin 负责包装与分发；runtime 负责状态和执行契约。不要为本 MVP 增加第三方插件发现框架。原生 Hook 是可选接入，缺失时核心接口仍正确；功能测试、模拟事件和实际客户端触发的证据分别报告。

## 9. 验收标准

所有项均需可定位证据；表中“独立检查”不能由 runtime 自报通过代替。本文维护标准，不提前填写通过状态。

| ID | 验收要求 | 检查方法与失败条件 |
|---|---|---|
| AC-001 | 跨对话继续同一 task | 两个不同 session 接续同一 ID；正文/范围保持；新建平行任务判失败 |
| AC-002 | 工作现场隔离 | 两个仓库、同仓库两个 worktree 各有任务；读写/清理不串用，逐项比较保留文件字节 |
| AC-003 | 原位修订与冲突保护 | 同一 task 多轮修改；旧 revision 写失败且新值不丢；重复操作不增加副本 |
| AC-004 | 四类 checklist 查询 | 全表、单项状态/详情、名称/内容命中与空结果；排序变化后 ID 稳定，越界明确失败 |
| AC-005 | 查询不制造材料 | 在初始化后的稳定现场反复查询；逻辑数据、revision 和受管材料集合不变；不要求 SQLite 内部字节不变 |
| AC-006 | 结果与验收分离 | 测试 pass、用户 pending/rejected 可同时成立；技术失败不伪装业务失败；Agent 自称完成不关闭 |
| AC-007 | 过期结果识别 | 改相关要求、配置和未提交代码分别触发失效；不相关修改有证据支持才保留有效 |
| AC-008 | 有限上下文恢复 | 新对话只取得当前范围、状态与必要引用；不自动返回全部旧报告/日志；现场 Git 状态重新核查 |
| AC-009 | 用户否决回到原循环 | 加入变更消息，更新同一 PRD/条件；保留未撤回要求，不新建平行文档 |
| AC-010 | Cleaner 任务收尾 | 只处理本 task 过程材料和关联工作现场；遵循项目已有保留/文档约定，无约定时按本 PRD 归属和引用规则处理；不引入代码质量治理。其他 worktree 和原有改动不变。长期信息进入合适既有载体，无必要不新增文档；独立 reviewer 检查遗漏和无意义搬运；等价迁移重验后关闭，行为变化返回原任务协商 |
| AC-011 | 清理边界正确 | 本 task 可删材料被删；项目文档、他任务、被引用/变更/越界材料保留；故意构造错误目标必须失败；显式保留完整 PRD/状态后关闭再重开，内容及引用不丢 |
| AC-012 | 清理可恢复 | 在各关键阶段中断再重试；剩余项完成，重复项不误删；未完成不能 closed |
| AC-013 | 旧 records 依赖迁移 | 验收脚本迁移后移除旧材料仍能测试；故意破坏被测行为必须变红；不得放宽断言 |
| AC-014 | 持久化与安装安全 | 默认/覆盖路径按约定解析，不因 cwd 变更分裂数据库；隔离目录实测权限失败、CLI 重启及双 data-root；升级成功保留、失败可恢复；卸载不自动清数据 |
| AC-015 | 无 Hook 正常使用 | 未安装/未信任 Hook 时完整循环可执行；正常项目写文件无需登记许可 |
| AC-016 | 写作和测试质量 | 按既有写作规范与测试规范独立 review；报告可独立理解、证据准确；有明确漏测/不符规范即失败 |
| AC-017 | 简化历史数据集有效 | H01–H05 在临时现场用 CPU、无网络/GPU/队列运行；不接触原 workspace；保留失败机制与必要干扰项；oracle 能检出注入错误 |
| AC-018 | 验证与结论相关 | 完成 §10.3 机制映射及必需负例；模型对照非默认门槛，只在有明确问题/预算时开展；不以功能测试冒充模型收益或消融结论 |
| AC-019 | 原子更新与文件发布 | 数据库多步修改中注入异常，验证全旧或全新；文件写入/替换阶段中断，读者不见半写结果；关联记录不得指向未提交产物；已有 committed 产物替换后、DB 提交前中断，并发读取不得成功返回混合版本，恢复后版本/摘要/内容一致 |
| AC-020 | 幂等与崩溃恢复 | 同键同请求串行/并发/跨进程重试仅提交一次；同键异请求明确冲突；提交后响应丢失重试返回原结果；跨 DB/文件各阶段中断后恢复，范围外材料不变 |
| AC-021 | 写入失败可见 | 权限不足、模拟磁盘写失败、数据库锁竞争与超时均不报成功；恢复存储后重试不丢已提交数据、不重复产物；不对外部命令宣称 exactly-once |

## 10. 测试、历史场景与消融

### 10.1 三类证据分别维护

- 回归测试：保留现有受限执行、revision、证据真实性和写作约束等有效行为；确定性测试无需模型。
- 新要求检查：针对 AC-001～AC-021 增加行为测试，特别是查询语义、外置存储、冲突和 closeout。沿用 unittest/tempfile，创建真实 Git worktree 和子进程中断；不因新测试强制切换 runner。
- 真实场景验收：从实际历史中提取最小可复现现场，再由真实 Agent 完成；独立检查最终代码、文件和语义质量。

重放固定工具调用只验证软件，不证明模型会选对操作。模拟 Hook 成功不等于原生触发成功。结构完整不等于语义正确。

### 10.2 从历史提取 CPU 简化数据集

构建 agent-tools 自己维护的初始小型数据集，保存最小代码 fixture、用户消息序列和独立判定脚本。历史用于定位机制，不运行原 workspace，也不整体复制生产仓库。所有案例均标为 adapted historical case，记录来源、简化内容、保留的失效机制和不能证明的事情。

| Case | 最小 CPU 场景 | 保留的机制/干扰项 | 对应标准 |
|---|---|---|---|
| H01 顺利开发 | 小型文件转换 CLI 的功能修改、测试与接受 | 真实输入输出、已有项目文档、无关文件；不为制造优势加入困难 | AC-006/010/016 |
| H02 需求修改 | 修改 CLI 的默认参数并追加一项约束 | 第一轮已通过结果、未撤回要求、可变 ordinal 和稳定 ID | AC-003/004/007/009 |
| H03 对话接续 | 新 session 从已有 task 恢复中断的 CPU 操作 | 不给旧对话正文；未完成项、禁止动作和有歧义的任务候选 | AC-001/008 |
| H04 过程膨胀 | 连续查询、重复提交与若干次真实修订 | 相同操作重试与有意义新结果分开；旧状态不能一直作为当前状态输出 | AC-003/005/008 |
| H05 收尾依赖 | 小型测试从旧 records 读取固定输入，迁移成正式 fixture | 被引用材料、无关项目文档、第二 worktree、用户保留文件、中断和内容变化 | AC-002/010/011/012/013 |

例如 Slime 中“验收脚本依赖将被清理的 records”提取为读取一个小 JSON fixture 的 CPU 测试；不保留 GPU 训练、模型权重、Pueue、SSH 或真实服务器路径。该案例证明依赖处理和清理边界，不证明训练正确性、GPU 恢复或远端执行安全。

所有运行创建临时 Git 仓库/worktree 和临时 data-root；不继承生产配置、凭据、原任务绑定或远程命令。先核查 fixture 和命令只读写临时根；配置错误指向原工作现场时测试必须拒绝执行。数据集中保留未跟踪原有文件、其他 worktree、用户保留材料和范围外资源哨兵，验证整理不越界。数据集默认无网络、无 GPU、无外部队列依赖。

每个 case 固定：初始文件及摘要、用户消息/投递时机、允许操作、预期结果和独立 oracle。数据集格式使用既有测试组织，不另建评测服务。原始聊天只保留必要脱敏摘录及来源，不提交大日志或秘密。

“简化”不能移除待验证的困难：保留并发旧 revision、多个任务候选、被引用文件等必要条件；设置至少一个邻近正常样例防止全部拒绝也通过。先让 oracle 在正确行为上通过，再注入遗漏、错删、错误有效性等故障确认会失败。

数据集分两种消费方式：确定性驱动验证 runtime；真实 Agent 执行验证接口是否可用和语义流程。前者先实现且无需模型；后者在隔离 CPU 场景中实测，但不等于真实 GPU/生产现场验收。当前尚未构建，不宣称已有可运行数据集。

### 10.3 验证问题、机制对照与可选模型实验

原 v1 的 A“精简 Skill＋原生工具”对 B“同样工具＋runtime”是产品级对照，不能定位某个功能的因果贡献。它与本项目有关，但只有在要回答“接入成本是否换来更好的任务完成/恢复”时才有价值；不能检验 SQLite 是否正确、某个检查条件是否过期，也不能仅凭小任务得分判断整个架构有用。因此不作为本 MVP 默认必跑的消融门槛。

本 MVP 首先验证以下明确问题：

| 问题 | 机制与数据集 | 方法 | 可以得出的结论 |
|---|---|---|---|
| 是否阻止旧对话覆盖新要求 | revision check；H02 | 两个写入者读取相同 revision，先后写入；故障版本移除检查后 oracle 必须检出丢失更新 | 并发控制覆盖了此故障，不是模型更聪明 |
| 结果是否正确失效 | 输入摘要/需求关联；H02 | 正常变更应失效；临时故障版本跳过失效，oracle 必须判错 | 有效性机制必要且此案例受覆盖 |
| 是否阻止误删 | ownership/reference/content 检查；H05 | 精确坏目标和正常可删目标；只在临时 fixture 中分别注入防护缺失 | 清理防护与判定器能识别已定义错误 |
| 查询与重试是否造成增长 | 无副作用查询/幂等提交；H04 | 固定操作序列前后比较逻辑状态、受管文件数量和大小；注入重复追加行为验证负例 | 软件是否满足无重复副作用契约 |
| 新会话能否通过接口找到必要信息 | task read/search；H03 | 先确定性验证返回数据，再让真实 Agent 在无旧聊天上下文下接续 | 接口完整性与该案例上的实际可用性 |

故障注入/受控机制关闭属于软件验证（可用 mutation testing 思路），不是 LLM 效果消融。故障版本仅存在测试隔离范围，不引入生产开关来关闭清理保护。每个测试检查外部可见后果，不能只是复述内部实现或只接受 runtime 的 pass 字段。

若需要模型对照，先提出单一假设，例如：“相比一份允许原位维护的普通任务记录，task 查询是否降低 H03 的遗漏约束和恢复错误，且不会增加过多操作。”只对相关 case 比较：

- A：固定精简指导＋Harness 原生读写/Shell/Git＋项目测试，允许普通任务记录；不暴露新旧 runtime 和干预 Hook。
- B：相同指导与原生工具＋task runtime 的必要接口说明。

测的是接口及其使用方式的整体作用，不单独归因于 SQLite。两组有同等任务信息与合理恢复手段，不故意削弱 A。默认串行；模型、Harness、Skill、初始 fixture、时间/token 上限一致。冻结预算、重复次数和失败处理后再比较，不看到有利结果就停。隔离 Harness 的已安装全局指令/Hook；无法隔离时标记混杂。

对 H03 主要观察遗漏约束、恢复错误和所需人工纠正；对 H04 如开展比较则观察任务成功前提下的文件/字节增长和过期状态引用。token、时长为成本指标。低错误基数或预算不足时可得“未观察到差异/证据不足”，不能声称等效或普遍提升。

保存可获取的实际轨迹、工具输入输出、最终 diff 与文件清单；先做少量 smoke 确认可观测性。轨迹或 token 缺失明确记 unavailable；无法观察的指标不作结论。语义质量按固定规范独立 review，无法真正盲评时披露。评测证据由评测任务持有，不被被测 task 的 closeout 删除；完成评估后有界保留，不扩散成产品的历史上下文。

### 10.4 通过与结论

- 功能交付：AC-001～AC-021 适用要求通过；数据集可在隔离 CPU 环境运行，独立 oracle 经正反例验证。
- Agent 场景验收：使用简化数据集完成需求修订、跨对话接续与收尾等实际工具调用，独立核查结果和写作/测试质量；不需要先比较 A/B 才能验证产品可用。未实测则单列未完成。
- 模型对照：按 §10.3 有明确问题时选做，不是必需交付或默认阻塞；没有运行就不宣称效果提升。
- 所有结论注明对象：软件契约、简化场景可用性、模型对照收益分别报告。数据集通过不能证明原生产现场或 GPU 功能通过。

## 11. 实施顺序与未冻结事项

## 12. 参考实现与经验

- [VS Code workspace/global storage](https://code.visualstudio.com/api/extension-capabilities/common-capabilities#data-storage)：借鉴工作区状态与工具全局状态分离，不照搬跨机器同步。
- [Python sqlite3](https://docs.python.org/3/library/sqlite3.html)：无独立服务的事务存储，使用明确提交/回滚。
- [platformdirs](https://platformdirs.readthedocs.io/en/latest/explanation.html)：应用数据与配置、缓存分开。
- [Git worktree](https://git-scm.com/docs/git-worktree)：识别实际工作树与共享仓库，不把分支名当永久身份。
- [Unit of Work](https://www.cosmicpython.com/book/chapter_06_uow)：一次业务修改作为提交单位；不意味着数据库事务能包住文件删除。
- [pytest temporary directories](https://docs.pytest.org/en/stable/how-to/tmp_path.html)：隔离测试存储与项目副本。

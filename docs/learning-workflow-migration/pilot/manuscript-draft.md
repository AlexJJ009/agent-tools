# Fixture Draft — Not for Submission as Empirical Results

This document is based entirely on synthetic, evaluator-supplied observations. The cases described below were not executed as part of this writing task, and the draft does not claim real-world validation, statistical generalization, or priority over prior work. No citations are included because the supplied materials contain no real bibliography.

## Introduction

Computational experiments are governed by agreements that connect a research question to the configuration ultimately consumed by a model, generator, or scorer. Those agreements often contain details that appear operational but can change the meaning of a comparison: how many candidates are generated, whether a token limit applies to the response alone or to the combined prompt and response, and which representations a scorer treats as equivalent. A pipeline may nevertheless run to completion when any of these details is implemented incorrectly. Successful execution therefore establishes that a program ran, but not that it ran under the conditions required to support the intended inference.

This distinction is especially important when several mechanisms change together. In the supplied synthetic source cards, increasing the number of candidates from one to four coincides with a larger aggregate maximum output budget, so an accuracy difference of 40% versus 44% cannot be attributed specifically to candidate diversity. A second fixture holds the stated candidate count and per-answer token cap fixed and reports 42% versus 43%, but changes both the generation procedure and indicators of candidate quality; with only one run per condition, it likewise does not isolate diversity or quantify uncertainty. A third fixture shows that normalizing leading zeros changes 5 of 50 answer-pair judgments, demonstrating that scoring rules can alter reported outcomes even when generated answers are unchanged. Together, these examples motivate a narrower prerequisite for trustworthy comparison: before interpreting performance, researchers should verify that the components which consume experimental settings and outputs implement the agreement actually under study.

We examine consumer-side readback as a lightweight way to perform this verification. Rather than checking only the declared configuration or the process exit status, a checker compares a supplied experimental agreement with the final values observed at the point of use. This design targets a specific class of setup error: a requested value may be syntactically valid and allow the program to complete, yet acquire a different meaning through defaults, aggregation, or scoring logic before it reaches the consumer. Reading the consumed value makes that semantic discrepancy visible. The checker is not intended to evaluate model quality, prove the validity of an experimental hypothesis, or replace tests of the underlying algorithm; it verifies whether selected conditions were instantiated as agreed.

The accompanying fixture evaluates this mechanism in three local, CPU-only cases, each containing one deliberately injected mismatch. The first requires four candidates per generator but exposes a consumed value of one. The second requires an 8,192-token response cap but applies 8,192 tokens to the prompt and response combined. The third requires integer-answer normalization but rejects `"007"` when the reference is `"7"`. Under the stipulated fixture outcomes, consumer-side readback identifies all three mismatches, whereas a comparator based only on successful program exit identifies none because every program exits successfully. These results support a bounded claim: for the three constructed cases, inspecting final consumed values distinguishes agreement violations that execution status alone cannot detect.

This study should therefore be read as a mechanism demonstration, not as evidence of downstream learning gains or operational reliability. The fixture includes no GPU training, production deployment, accuracy study of the checker, estimate of researcher time saved, or repeated sampling from a broader population of errors. It also does not establish that consumer-side readback is novel. A substantive evaluation must test the approach against a larger and independently assembled error set, record both false negatives and false positives, and determine when an observed mismatch materially changes a scientific conclusion. Within these limits, the present demonstration identifies a concrete verification target and a baseline that is too weak for it: an experiment can execute successfully while violating the conditions its result is meant to represent.

## Alternative Proposal Direction: Budget-Matched Causal Audit of Candidate Generation

An alternative project could shift from demonstrating setup-error detection to testing whether candidate count or generation procedure improves answer accuracy under a fixed inference budget. The central hypothesis would be: **after total generation tokens, scoring rules, model, and evaluation questions are held constant, a four-candidate condition improves accuracy relative to a one-candidate condition because it supplies useful answer variation.** This hypothesis is intentionally stronger than the supplied evidence and would be treated as unverified until the proposed study is run.

The study would use a preregistered 2 × 2 design crossing candidate count (one versus four) with generator procedure (baseline versus diversity-oriented). Each question would receive the same total response-token allowance in every condition; the one-candidate condition could spend the full allowance on one response, while the four-candidate condition would divide it evenly across four responses. The base model, prompt template, question set, candidate selector, and integer-normalization rule would remain fixed. Multiple seeded runs would be used so that uncertainty is estimated across runs rather than inferred from a single comparison. In addition to final accuracy, the study would record candidate-level correctness, selection oracle accuracy, realized token use, the rate of distinct normalized answers, and the fraction of decisions changed by normalization. These measurements would separate three possible bottlenecks: generating a correct candidate, generating meaningfully different candidates, and selecting correctly among them.

A modest pilot could remain CPU-only and use a fixed set of questions with, for example, five preregistered seeds per cell; its purpose would be to estimate variance and determine whether a larger evaluation is warranted, not to establish a universal effect. The primary contrast would compare one versus four candidates after matching total token use. The interaction between candidate count and generator procedure would test whether any advantage of multiple candidates depends on the way variation is produced. All configuration values would be read back at their consumers, preserving the verification mechanism from the current fixture while applying it to the proposed causal comparison.

The proposal would be falsified in its present form if the budget-matched multi-candidate condition failed to improve accuracy beyond the preregistered minimum effect, or if any apparent gain disappeared when scoring and realized token use were controlled. It would also be weakened if increased answer diversity were not associated with a higher probability of containing a correct candidate, or if gains arose only from the selector rather than the generator. Conversely, evidence for the hypothesis would require repeatable accuracy gains under matched budgets, verified consumer-side conditions, and an analysis showing that the multi-candidate condition improves candidate coverage rather than merely exploiting a scoring artifact. This design directly addresses the confounds in the supplied source cards while keeping the proposed outcome separate from the fixture results already available.

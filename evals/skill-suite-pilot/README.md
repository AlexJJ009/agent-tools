# Agent Tools skills 评测设计试用

这次使用项目内的 `build-eval`，先把“这些 skills 是否有用”拆成可观察的问题。
当前交付是题目和评分设计草案，没有运行正式 Agent 评测，没有生成用户偏好标签，
也没有开始 hillclimb。源代码基线为 `168906a4e4471a814a15a3a851cebcc6093c4005`，
包含最新学习套件和已合入 main 的 Codex eval 适配。

## 先看什么

从本目录的 `REVIEW.md` 看完整候选题及判定条件；`design.json` 保存维度、依据和
评测方法，`cases.json` 保存候选输入及环境材料。它们都属于实验分支的设计资产，
不是已经认可的标准答案，也不是当前 skills 的成绩。

结合本轮反馈，建议先看 C05（抓根因）、C11（清理与交接）、C18（必要 ADR）和
C19（自然触发练习）。同时保留“不要求就不产 Work Report、不堆过程文档”的正向边界。
C18 有明确文档检查请求及项目 ADR 约定，暂不能证明无提醒时也会主动维护。

这次分开考察四组任务，不计算混合总分：

| 任务组 | 我们希望知道什么 | 应看什么证据 |
| --- | --- | --- |
| Agent workflow | 是否保持当前任务、约束和证据边界，并实际完成工作 | 文件变化、测试结果、状态读回、调用轨迹 |
| 教学重建 | 解释是否准确，是否把问题、前提和机制连起来，并适应反馈 | 固定来源核对、完整解释、用户匿名 A/B 判断 |
| 练习 | 是否自然触发、容易看到、适合目标，是否正确记录帮助程度 | 当前回复中的练习题、实际回答及反馈 |
| 学习材料 | 是否交付所请求的材料，草稿是否被错误当作正式归档 | 材料与记录变化 |

每组还要按具体流程独立运行和报告。例如“代码讲解”与“显式知识归档”不能靠同一个
成功率掩盖差异。先用少量候选题验证题目是否清楚，再确定真正需要运行的流程。

## 三种结论要分开

**程序通过单元测试**，说明校验器或 runtime 在指定输入下工作；它不证明 Agent
会理解用户的话。**Agent 完成任务**，说明某个配置在该场景下表现正确；它还不能
证明是目标 skill 带来的帮助。**相同环境下加入 skill 后更好**，才是该 skill 的
增量效果证据。

教学还多一层：用户更喜欢 B 的解释，不等于 B 让用户学得更好。学习成效需要用户
真正完成新情境中的任务，必要时隔一段时间再测。模拟学生可以检查练习流程，但不能
替代真实人的迁移和保持表现。当前不对用户安排学习实验。

## 如何比较有无 skill

保留相同模型、工具、初始文件、其他规则和预算，只改变目标 skill 是否可见。
另一个比较是固定旧版与新版。每次使用全新环境，轮换两组执行顺序，并重复关键题。
先报告逐题改善和退步、约束违反、耗时及用量，再决定是否适合汇总。

必须记录被测 skill 的源码版本以及实际安装字节。移除目标文件不等于消除了它：
全局 AGENTS、其他 skill 或依赖可能仍携带同样规则。因此“没有差异”可能代表冗余、
题目无区分度或抽样太少，不能直接宣布 skill 没用。显式加载可测内容效果；正常发现
路径可测选择与加载效果，两种实验需分别命名。

这些设计文件和评分标准留在评测端。真正执行时，只把题目和必需 fixture 放入被测
Agent 的工作目录，不能把本工作树及 Git 历史当作防泄漏隔离。worktree 隔离开发改动，
并不隔离同一用户能访问的文件；正式 runner 还需要单独的工具和文件访问边界。

## 用户 A/B 标注怎么用

先检查事实和明确约束，再向用户展示匿名、随机左右位置的两个产出。允许选择 A、B、
同样好、都不好或跳过，附一句原因和适用场景。选择记录要绑定具体题目、两份产出和
版本；这些字段在有真实产出、真实选择前保持空值。

一次“喜欢短一点”只能说明这道题的偏好，不自动变成所有场景的长期规则。不同任务
可能需要不同篇幅。重复出现且用户确认的偏好可以成为后续 rubric 的候选修改；修改
rubric 后需要重新评分，不能把新旧分数直接比较。

校准模型评分器时，使用一部分真实用户标签调试，另一部分保留做独立核对。匿名和
独立会话不能消除模型的共同偏好。发生分歧时保留双方理由，不把用户标签改成模型答案。

## 本轮校验及下一步

本轮只核查设计的结构、来源位置、维度覆盖、题目与判分条件是否一致，以及是否存在
“什么也不做就得分”的漏洞。文件可解析和独立审阅通过都不表示题目代表真实使用分布，
也不表示评分器已与用户判断一致。

现成素材包括 `tests/fixtures/learning_workflow/validation-cases.json` 的合成规则题，
以及 `tests/fixtures/task_runtime/cases.json` 的历史场景改编。候选题沿用或扩写这些机制，
本轮用户反馈已用于选题，原话与不确定性保存在 design.json 中；候选材料仍是合成改编，
没有复现 PHAI 或 read paper 的真实故障。没有读取私人聊天历史、外部日志或论文库。

C11 另要求评测端记录初始、运行中和最终文件状态，区分“没有生成”和“生成后清理”。
这是评测端的证据义务，不要求被测 Agent 回答它看不到的观察器日志，也不计入 Agent 成绩。

按 BuildEval 的原始流程，正式运行前分两次审阅：先确认输入是否代表你关心的任务，
再用少量真实输出确认评分是否符合你的判断。原文要求：
“There are two sign-offs you always need - the inputs and the grading method.”
见本仓库 `.agents/skills/build-eval/SKILL.md`。当前用户授权的是产出并检查设计，
不是预先认可候选题或评分器；因此草案均保持未批准状态。

建议先选择一个流程验证，保留其他流程为候选，不马上把所有 skills 跑成一个大榜单。
实验分支 `codex/skill-eval-design` 独立于 main；是否采用其设计仍由审阅决定。

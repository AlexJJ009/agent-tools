# H06 来源定位跟进

原 H06 的四次输出都要求用户重新贴函数，没有读取现有 `cleanup.py`；skills 组读了技能及出题参考，但没有查项目源码。
原对话中的“这两个函数”没有项目或文件锚点。因此这首先是来源定位不明确的诊断，不能称为 finally 推理或练习设计失败。

本组提前固定两个最小变体，各跑 skills/control 两次，共 8 个试次：

| 题目 | 最后一轮用户请求中的唯一条件变化 |
| --- | --- |
| S01 | “用当前项目里的这两个函数就行” |
| S02 | “用当前项目cleanup.py里的两个函数就行” |

其他源码、历史对话、用户精力与先不揭答案的要求、技能消融配置、主能力标准和 oracle 保持与 H06 相同。
只有题目身份元数据及最后一句来源位置变化。`followup_design.source_grader_case_id` 将两题映射回 H06 的评分逻辑，check ID 改为对应 S01/S02。
不能为了让定位条件产生差异而更改代码难度或偷偷增加新的评分要求。

## 运行前固定的解释规则

- 两个变体都正确读取源码并出题：原失败符合缺少项目定位的解释，尚无 finally 能力缺口证据。
- 项目线索下重复不查源码，明确路径后读取并通过：定位到弱线索下的主动源码发现不足；不能说不懂 finally。
- 已读源码但题目错误：继续检查练习构造或源码推理，不能再归咎没找到文件。
- 明确路径后仍不读取且要求贴代码：属于来源使用/执行缺口；没有实质答案时，不能推断知识推理错误。
- 两组模式相同：先归于共同 Agent 行为或上下文限制，不能据此宣称目标 skill 的增量效果。
- 两次重复里一组不同：仅作局部配对证据，还不足以证明稳定收益或损害。

来源发现证据单独记录，不变成新的主评分条件。可接受不同搜索、浏览或直接读取方式；要看实际工具结果是否拿到代码，不能只凭命令出现文件名。
评分仍检查题目能否对照两函数、给出 work 抛错且 close 正常返回的充分条件，并形成可判别、未提前泄答案的短题。

这两题及因果解释应在运行前提交冻结。保留旧 H06 题目、原输出与评分，不将它们覆盖成新提示下的结果。

## S03：学习记录定位探针

机制轮L01首次skills输出未读取现有record，转而用共享写作规则中的缓存/429例子出写作题。
S03仅在原请求中加上“当前项目 learning-record.json 记录的”，源码、原记录和评分要求均不变。
若明确路径后恢复目标与未答题，问题位于状态发现而非浅拷贝知识；若仍偏题，再查读取后使用链。
原输出不改，不把未明确来源时编造的主题算作实际学习延续。总计3题，两组各2次，共12试次。

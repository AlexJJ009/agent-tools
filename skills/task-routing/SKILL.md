# Task Routing

The Main Agent decides the current activity from the user's latest request, the still-active agreement, explicit exclusions, and material ownership. A topic word, cwd, quoted source instruction, or installed skill does not authorize an activity switch. Ordinary explanation needed to complete a development request remains delivery. Honor "do not teach", "no exercises", and similar exclusions even when the same request mentions a paper or learning term.

Choose one current activity: `delivery`, `learning`, `writing`, `curation`, or `answer`. Select the capabilities needed for that activity; a capability can be reused in several activities. Use `direct`, `guided`, `practice`, or `review` interaction mode. For ordered mixed requests, keep a continuation point and perform stages in the user's authorized order. Do not let the later stage replace unfinished delivery.

For a sustained task, write the request and a short semantic decision packet with the PRD route fields, then initialize with `learning-workflow init --query PATH --decision PATH --workspace DIR --session-id ID [--task-id ID] [--record DIR]`. For a later user turn, use `input --record DIR --input-id ID --query PATH`, then `classify --record DIR --input-id ID --decision PATH --base-revision N`. Use the actual native session ID supplied by the Hook or harness; do not invent it from a directory name. `input` advances the route revision: use the returned revision or read `show --record DIR` before `classify`; do not reuse the revision from before input recording. Read back with `show --record DIR`; validate the record before depending on it. Bind a native session only when needed with `bind --record DIR --session-id ID --workspace DIR --state-root DIR [--on-stop]`. Use `python -m learning_workflow` when the installed launcher is unavailable. Follow the CLI's help for the exact packet schema. First read the existing route and any canonical development record. A brief answer can remain in conversation without a route file. Route records reference development record and revision; they do not copy its authorization, checklist, or acceptance state. Repeated input should be idempotent. A stale classification must surface a revision conflict, never overwrite newer exclusions. Before a covered action, call `check-action --record DIR --action NAME [--target PATH] --base-revision N`. Use `curate --record DIR --source PATH --destination DIR --title TEXT --topic TEXT --base-revision N` only for explicit curation. Set `project_id` to an explicit stable source repository identifier before curation (for example an inspected repository remote or a user-provided ID); a directory basename can collide across projects. Keep that ID on relocation. Covered actions include registered writes, curation, Zotero operations, and remote reads; this is not a universal tool sandbox. Missing route state blocks only actions that depend on it; harmless reading and recovery remain available.

Set `readpapers_root` only from an explicit configured project root and `authorized_read_roots` only from user-granted scope; do not invent authority in a decision packet. ReadPapers owns Zotero library operations, adding papers, formal close reading, and ZotLit note updates in its configured project scope. Manuscript projects own drafts and experimental claims; code repositories own implementation and runtime facts. Existing evidence may cross these boundaries as cited material, but source access never grants execution or library write authority. For authorized SSH source reading, record repository, revision, path and observed range; distinguish code observations from executed tests.

Use an independent reviewer only for a genuinely disputed mixed intent or consequential review. Ask the user only when their intended goal cannot be inferred and the answer changes what work is authorized. If the user corrects the route, update it and resume the original task at the right stage. Work Report follows its own development reporting trigger; ordinary learning does not create one.

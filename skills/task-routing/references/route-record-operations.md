# Route record operations

Read this when creating, resuming, binding, or acting through a persisted route.
Select the current activity and authority using `../SKILL.md` first.

Create a route only for a learning/writing task that must continue across sessions or tasks; reuse an existing route for the same task. Initialize with `learning-workflow init --query PATH --decision PATH --workspace DIR --session-id ID [--task-id ID] [--record DIR]`; the request and decision packets are transient inputs under `docs/_local/scratch/<task-id>/`. `learning-workflow decision-schema` and CLI help give the packet shape; use `python -m learning_workflow` when the installed launcher is unavailable. Use the actual native session ID supplied by the Hook or harness, never one derived from a directory name. Read back with `show --record DIR` before depending on the record. Bind a native session only when needed with `bind --record DIR --session-id ID --workspace DIR --state-root DIR [--on-stop]`.

Record and classify a later input only when it changes the persisted route (activity, exclusions, scope, or outputs): `input --record DIR --input-id ID --query PATH`, then `classify --record DIR --input-id ID --decision PATH --base-revision N` at the revision `input` returned. In a bound session the Hook saves each prompt as pending input; classify pending input before curation or another dependent action. Repeated input is idempotent; a stale classification surfaces a revision conflict and never overwrites newer exclusions.

Route records reference the development record and revision; they do not copy its authorization, checklist, or acceptance state. Before a covered action, call `check-action --record DIR --action NAME [--target PATH] --base-revision N`. Use `curate --record DIR --source PATH --destination DIR --title TEXT --topic TEXT --base-revision N` only for explicit curation. Set `project_id` to an explicit stable source repository identifier before curation (for example an inspected repository remote or a user-provided ID); a directory basename can collide across projects. Keep that ID on relocation. Covered actions include registered writes, curation, Zotero operations, and remote reads; this is not a universal tool sandbox.

For an existing development record, `development_record_ref.path` is the directory containing its `checklist.yaml` or project-equivalent `task.md`, not the Markdown file itself. Read its actual revision and attach the route sidecar to that directory; omit `--record` or supply the same directory. Referencing a Markdown task record preserves its ownership; it creates no execution or acceptance authority.

When a persisted route covers explicitly ordered stages, classify a stage on entry only if it changes the route; `next_stage` records a plan, not an executed transition. Reuse the original request with a distinct stage input ID. Before finishing, reread the canonical development record and refresh its referenced revision if it changed. Carry the requested repair scope through every stage; a repository's list of other defects does not expand that scope.

Recover a failed capability or action check in the existing record. Inspect the actual installation first. Default capability discovery includes the user's and the workspace's `.agents/skills`, legacy `.codex/skills`, and Claude Code `.claude/skills`; supply explicit `skill_roots` only for inspected nonstandard locations. If the decision needs a technical correction, record the current preserved request with a distinct recovery input ID, then `classify` at the returned revision and explain the correction in `rationale`. This repeats existing request evidence, not new user permission. Preserve the task ID, session ID, exclusions, and authority. If capability remains unavailable, disclose the gap and continue only supported work.

# Route record operations

Read this when creating, updating, binding, or recovering a persistent route,
or using an existing route for covered actions or curation.
Select the current activity and authority using `../SKILL.md` first.

For a sustained learning/writing task or an authorized cross-activity handoff, write the request and a short semantic decision packet with the PRD route fields, then initialize with `learning-workflow init --query PATH --decision PATH --workspace DIR --session-id ID [--task-id ID] [--record DIR]`. For a later user turn, use `input --record DIR --input-id ID --query PATH`, then `classify --record DIR --input-id ID --decision PATH --base-revision N`. Use the actual native session ID supplied by the Hook or harness; do not invent it from a directory name. `input` advances the route revision: use the returned revision or read `show --record DIR` before `classify`; do not reuse the revision from before input recording. Read back with `show --record DIR`; validate the record before depending on it. Bind a native session only when needed with `bind --record DIR --session-id ID --workspace DIR --state-root DIR [--on-stop]`. Use `python -m learning_workflow` when the installed launcher is unavailable. Follow the CLI's help for the exact packet schema. First read the existing route and any canonical development record. A brief answer can remain in conversation without a route file. Route records reference development record and revision; they do not copy its authorization, checklist, or acceptance state. Repeated input should be idempotent. A stale classification must surface a revision conflict, never overwrite newer exclusions. Before a covered action, call `check-action --record DIR --action NAME [--target PATH] --base-revision N`. Use `curate --record DIR --source PATH --destination DIR --title TEXT --topic TEXT --base-revision N` only for explicit curation. Set `project_id` to an explicit stable source repository identifier before curation (for example an inspected repository remote or a user-provided ID); a directory basename can collide across projects. Keep that ID on relocation. Covered actions include registered writes, curation, Zotero operations, and remote reads; this is not a universal tool sandbox. Missing route state blocks only actions that depend on it; harmless reading and recovery remain available.

Keep request and decision scratch files inside the current workspace or an explicitly authorized existing record directory. Temporary routing inputs are still writes subject to the task's scope; do not move them to a system temporary directory when writes are limited to the workspace.

For an existing development record, `development_record_ref.path` is the directory containing its `checklist.yaml` or project-equivalent `task.md`, not the Markdown file itself. Read its actual revision and use that directory for the route sidecar; omit `--record` or supply the same directory. Do not create a second task record or fabricate a checklist merely to attach learning. Referencing a Markdown task record preserves its ownership; it creates no execution or acceptance authority.

For a persistent task with explicitly ordered delivery, learning, and resumed delivery, classify each authorized stage when entering it; `next_stage` records a plan, not an executed transition. Reuse the original request with a distinct stage input ID, then call `classify` at the returned revision. This is progress within the existing request, not invented user permission. Before finishing, read the canonical development record again and refresh its referenced revision through the same update path if it changed. Carry the requested repair scope through every stage; a repository's list of other defects does not expand that scope.

Recover a failed capability or action check in the existing record; do not initialize a replacement record for the same task. Inspect the actual installation first. Default capability discovery includes the workspace's `.agents/skills` and legacy `.codex/skills`; supply explicit `skill_roots` only for inspected nonstandard locations. If the decision needs a technical correction, record the current preserved request with a distinct recovery input ID, then use `classify` at the returned revision and explain the correction in `rationale`. This repeats existing request evidence, not new user permission. Preserve the task ID, session ID, exclusions, and authority. If capability remains unavailable, disclose the gap and continue only supported work.
